# 答辩问答（36 题）

按"设计取舍 → 文件系统 → 内存 → 设备 → 进程 → 界面 → 测试 → 局限"分组。
每题的答案都对应具体代码，答不上来时可以直接翻文件。

## 一、总体设计与规格

### Q1 这个系统到底"模拟"了什么？哪些是真的，哪些是假的？

**真**：磁盘是一个真实的 16 KB 文件（`disk.img`），FAT、目录项、文件内容都真实写在里面，
重启后还在；进程的指令真的被装入内存数组并从内存取指执行；设备真的按时间单位倒计时；
时间片真的会让进程切换。

**假**：没有真实的中断控制器、没有 MMU、没有特权级；
"内存"是一个 `byte[512]`，"设备"是三个整数（占用者、剩余时长、类型）。
这些是课程要求范围内的简化，且都在文档里写明了。

### Q2 课程说明要求"FAT 占第 0、1 块"又要"256 个表项"，你是怎么处理的？

这两条**互相矛盾**：256 项 × 1 字节 = 256 字节 = 4 个块，而 0、1 两块只有 128 字节。

处理方式：保留两条硬约束中更本质的部分——"FAT 必须 256 项"（否则无法覆盖 256 个块）
和"根目录固定第 2 块"（课程明确要求，且很多演示依赖它），
把 FAT 拆成**前 128 项放 0、1 块，后 128 项放 3、4 块**，块 255 保留。

代价是 FAT 物理上不连续；对上层完全透明，因为换算只发生在
`Fat.blockOfEntry(i)` 和 `Fat.offsetOfEntry(i)` 两个方法里。
`fdisk` 命令、README 第 3 节、`docs/FILESYSTEM.md` 第 2 节都记录了这个取舍。

### Q3 为什么块 255 要保留？

因为 FAT 用 255 表示"链结束"。如果 255 号块也能分配给文件，那么
"文件最后一块指向 255"和"下一块是 255 号块"就无法区分。所以 255 不参与分配。

### Q4 为什么文件名最多 3 个字符？

课程规定目录项 8 字节：3（名称）+ 1（扩展名）+ 1（属性）+ 1（起始块）+ 2（长度）。
这是硬约束，不是实现偷懒。所以默认文件叫 `P01.E`、`HLP.T`、`RED.T`。
如果想支持长文件名，需要改 `DirEntry.SIZE` 并同步改每块目录项数和所有相关测试。

### Q5 为什么不用多线程/多进程来模拟"多道程序"？

用真实线程 + `sleep` 会有三个问题：

1. **不可复现**：同一个程序跑两次，设备倒计时的先后顺序可能不同；
2. **无法单步**：调试时要"停在第 3 个时间单位、第 2 条指令"，线程模型做不到；
3. **容易出竞态**：两个定时器各扣一次设备倒计时，这类 bug 极难定位。

改用统一逻辑时钟后，`tick()` 是一个普通方法，测试里 `runTicks(6)` 就能精确断言
"P1 的 PC 应该是 6"。这是本项目最重要的工程决策。

## 二、文件系统

### Q6 FAT 表项 254 有什么坑？怎么发现的？

254 既是"保留块"的标记值，**又是最后一个数据块的块号**。FAT 表项只有 1 字节，
任何标记值都必然和某个块号重合。

最初的 `chainOf` 写的是"下一块 == 254 就当保留块，提前收尾"。
结果写一个占满磁盘的文件时，链走到第 253 块、下一块是 254，就被误判成坏链，
链长少 1，`writeNewChain` 里 `chain.get(205)` 直接抛
`IndexOutOfBoundsException: Index 205 out of bounds for length 205`。

修复：链遍历只看"下一块是否落在 5~254 的数据区范围内"；
保留块用 `Fat.isReservedBlock(blockNo)` 按**块号**判断，不看表项值。
回归测试 `chainCrossingBlock254IsNotTruncated`。

### Q7 一个文件是怎么存的？给我讲 294 字节的 N01.T。

`length = 294` → `blocks = ceil(294/64) = 5`。
`Fat.allocateChain(5)` 从低地址找到 5 个空闲块，串成链：
`b0 → b1 → b2 → b3 → b4(255)`。目录项记 `startBlock = b0`、`length = 294`。

读的时候 `readChain(b0, 294)` 沿链读 5 个 64 字节块，最后一块只取
`294 - 4×64 = 38` 字节。界面磁盘网格上这 5 格会标成 `\DOC\N01.T`。

### Q8 目录能放多少项？超过怎么办？

每块 64 字节、每项 8 字节 ⇒ 每块 8 项。

- **根目录**：固定占第 2 块，**不能扩展**，最多 8 项（默认用了 7 项）；
- **子目录**：可以扩展。`addEntry` 找不到空槽时申请新块、接到目录链尾，
  容量变成 16 项、24 项……

`\BIN` 有 10 个程序，所以占 2 块（`directoryBlockCount("\BIN") == 2`）。

### Q9 删除文件时目录项怎么处理？为什么不搬动后面的项？

只把名称首字节置 0（`DirEntry.clearSlot`），后面的项原地不动。
好处是删除是 O(1)，且不会因为搬动导致"找到一半的路径失效"。
查找时跳过首字节为 0 的槽位即可。

### Q10 写到一半磁盘满了，原文件会不会坏？

不会。`writeFile` 的顺序是"**先分配新链、写完内容，再释放旧链、更新目录项**"。
如果新链分配失败（磁盘满），直接抛 `FsException`，原文件一个字节都没动。

`createFile` 则是"先写链再写目录项"，如果目录项写不进去（比如目录满），
会 `freeChain` 回滚，不会泄漏块。

### Q11 打开文件表有什么用？被打开的文件为什么不能删？

表项记录读写指针，`read` 可以连续读（指针前移）。最多 5 项。
被打开的文件不能删/不能整体覆盖写，因为表项里还存着旧的 `startBlock`，
如果底层链被释放或替换，表项就指向了错误的位置——这是"一致性"问题，
直接拒绝比事后修补简单可靠。

### Q12 关闭程序再打开，文件为什么还在？

每次修改都会 `Fat.flush()` 把 256 项写回 4 个 FAT 块，文件内容直接写数据块，
目录项写目录块，最后 `disk.flush()`。`Disk` 用的是 `RandomAccessFile`，
数据在操作系统层面已经落盘。

重启时 `Fat.load()` 从 4 个块还原 256 项，`isFormatted()` 检查
块 0~4、255 是否都是保留标记——是就认为已格式化，不再重装默认树。

### Q13 相对路径怎么实现的？`chdir` 之后为什么能直接 `type N01.T`？

`Shell.currentDir` 记住当前目录，`resolvePath` 调用
`PathUtil.resolve(currentDir, raw)`：输入不以 `\` 或 `/` 开头时，拼到当前目录后面。
`FileSystem` 本身只认绝对路径，相对路径的解析在命令层完成——这样文件系统不用关心"谁是当前目录"。

## 三、内存管理

### Q14 首次适配是怎么做的？给个具体地址。

从低地址扫描分区表，第一个"空闲且长度 ≥ 需求"的分区就切走。
例如 512 字节全空，`allocate(P1,100)` 得到地址 0；再 `allocate(P2,100)` 得到 100；
再 `allocate(P3,50)` 得到 200。每次切走后在原位置留下一个空闲分区。

### Q15 为什么必须合并空闲分区？不合并会怎样？

反复创建/撤销进程后，512 字节会被切成很多 2~8 字节的小洞。
总量够但**没有一段连续空间**，就会"明明还有 300 字节空闲却装不下 100 字节"——
这就是外部碎片。`release` 时 `mergeFreePartitions()` 把相邻空闲区合成一块，
是首次适配能长期工作的前提。

### Q16 程序比内存还大怎么办？

`allocate` 返回 -1 时，进程不报错，而是进入**等内存队列**（状态 NEW）。
每个 tick 的第 ⑥ 步 `retryPendingProcesses()` 重试；
某个进程结束释放出足够大的连续分区后，它就会被装入并转为就绪（PC/X 复位）。

这个状态在界面 "等内存" 队列里能看到，答辩时可以现场演示。

### Q17 进程的指令存在哪？为什么删了源文件还能跑？

`createProcess` 时把文件内容（字节数组）通过 `memory.loadProgram()` 复制到用户区，
CPU 取指用 `memory.read(pcb.getMemoryStart() + pc)`。
所以运行中的进程和磁盘上的源文件已经没关系了。
`IntegratedScenarioTest` 场景二专门验证了这一点：运行中删掉 `P03.E`，进程照样跑完。

### Q18 一个进程能占两段内存吗？

不能。`allocate` 里检查同一 PID 是否已有分区，有就抛 `IllegalStateException`。
因为 PCB 只记一个 `memoryStart` + `memorySize`，多段会让寻址变复杂，
而课程要求的程序都很小（最多几十字节），没必要。

## 四、设备管理

### Q19 设备是怎么分配的？A 类只有 2 台，第 3 个申请的进程会怎样？

`DeviceManager.request` 遍历同类设备找一台空闲的：
找到就 `assign(pid, duration)`，返回 true；找不到返回 false，
调用方 `enqueue` 进该类型的等待队列（FIFO），进程转阻塞。

第 3 个进程会阻塞，阻塞原因显示"等待A类设备"，界面设备区的等待队列显示 `P3(3)`。

### Q20 设备倒计时归零后做了什么？

三步（`handleDeviceCountdown` + `handDeviceToNextWaiter`）：

1. `devices.release(device)` 释放；
2. `processes.wake(owner)` 唤醒原进程到就绪队列；
3. 如果等待队列非空，把设备**直接交给队首**，按它当初申请的时长重新倒计时。

第 3 步是优化：设备不空转，也不用让队首进程重新执行一次申请指令。
此时队首进程仍是 BLOCKED（它还没"用完"这台设备），等这台设备也用完才被唤醒。

### Q21 为什么不让人工唤醒"等设备"的进程？

因为它恢复执行后会从 `!A3` 的下一条指令继续，而设备还在别人手里，
后续状态立刻不一致（它以为自己用完了，实际没释放）。
所以 `resumeProcess` 检查 `pcb.getDeviceType() != null` 时直接返回 false。

### Q22 进程被撤销时，它占的设备怎么办？

`ProcessManager.destroy` 里 `devices.releaseAll(pid)` 释放全部设备，
`devices.removeWaiter(pid)` 把它从所有等待队列里摘掉。
不摘会造成"幽灵请求"：设备释放时按一个不存在的 PID 分配，之后没人释放，设备永久占用。
`handDeviceToNextWaiter` 还会再检查一次队首进程是否仍在阻塞，双保险。

## 五、进程与调度

### Q23 时间片中断时保存了什么？存在哪？

保存 PC 和 X 到 PCB（`cpu.saveTo(pcb)`）。内存起始地址、程序长度、时间片余量等
本来就在 PCB 里，不需要额外保存。`dispatch` 时 `cpu.restoreFrom(pcb)` 再取回来。

PC 指向"下一条要执行的指令"，所以执行了 6 条后 PC=6。
测试 `时间片 3 时两个进程交替推进` 断言切换后第一次执行的指令让 X 从 3 变 4，
直接验证了 X 也恢复了。

### Q24 为什么用轮转而不是优先级/最短作业优先？

课程要求"时间片轮转"。轮转的优点是不会饥饿、响应时间可预测；
缺点是不区分紧急程度、平均周转时间不如 SJF。

扩展很容易：`ProcessManager.dispatch()` 现在取 `readyQueue.pollFirst()`，
改成"遍历找优先级最高"就变成优先级调度（见 `LEARNING_GUIDE.md` 实验 7）。
但要注意优先级调度会有饥饿问题，需要老化。

### Q25 就绪队列为空时 CPU 在干什么？

跑"闲逛进程"（IDLE，PID=0），界面显示"就绪队列为空，CPU 运行闲逛进程"。
它不执行指令，但时钟照常推进（`addRunTime`），这样"系统在空转"是可观察的。

如果 IDLE 正在跑时突然有进程就绪（设备唤醒），同一个 tick 的第 ③ 步就让它让出，
新进程不用白等一个时间单位。

### Q26 一个 tick 内到底按什么顺序做事？顺序能不能换？

7 步：时钟+1 → 设备倒计时 → 调度 → 执行一条指令 → 时间片-1 → 重试等内存 → 随机到达。

不能随便换：

- 设备倒计时必须在执行之前，否则"本 tick 刚申请的设备"会被立刻扣一次；
- 调度必须在执行之前，否则新进程要多等一个 tick；
- 重试等内存放在执行之后，这样"本 tick 结束的进程释放的内存"能立刻被用上。

### Q27 随机到达怎么保证可复现？

`OperatingSystem` 构造时接收 `seed`，用 `new Random(seed)`；
到达间隔在 2~5 个时间单位之间随机。同样的种子 + 同样的 tick 数，结果完全一样。
测试和演示都可以关掉（`autoArrival=false`）。

### Q28 程序里的 X 超过 255 会怎样？

饱和处理：`x++` 在 255 时保持 255 并记录"X 已到上界 255"；`x--` 在 0 时保持 0。
不做回绕（`(x+1) & 0xFF`）是因为回绕会让"程序算错了"看起来像"正常执行"，
饱和更容易在日志里发现。`P06.E` 就是专门测这个的（`x=99`、`x++`、`x--`）。

## 六、界面与工程

### Q29 界面怎么保证不和模型状态打架？

界面**只读快照**。每个 tick 结束后 `OperatingSystem.snapshot()` 一次性复制
全部状态（进程、分区、设备、FAT、块归属、日志），8 个面板各自 `refresh(snapshot)`。

快照是拷贝（`PcbView` record、分区列表副本、FAT 数组副本），
所以面板即使乱序刷新也看到同一时刻的状态，而且改快照改不动模型。

### Q30 界面会阻塞模拟吗？

不会。所有操作都在 EDT 上：`SimulationDriver` 用一个 `javax.swing.Timer`，
回调里 `os.tick()` + `refresh()`。一次 tick 是纯内存计算 + 少量 64 字节磁盘 IO，
耗时在微秒级，不会造成可视卡顿。

速度滑块改的是 `Timer.setDelay()`，不会创建第二个 Timer——这是"只有一个时钟"的保证。

### Q31 命令层为什么要和界面分开？

因为**业务逻辑不该依赖 GUI**。`Shell` 只依赖 `OperatingSystem`，
返回 `CommandResult`；需要弹编辑器/确认框时通过 `EditorService` / `ConfirmService`
两个函数式接口注入。

好处很直接：22 条命令全部能在无界面环境下做单元测试（`ShellTest` 13 个用例），
`format` 的二次确认在测试里注入一个"总是确认"的 lambda 就行。

### Q32 中文显示成方块是怎么解决的？

等宽字体 Consolas 没有中文字形。`Theme` 里分成两套字体：

- 数字/十六进制/寄存器用等宽（`Consolas`）；
- 含中文的文本区、日志、命令输出用 `CONSOLE_FONT_NAME`，
  候选依次是 Sarasa Mono SC、新宋体、微软雅黑，并用
  `font.canDisplayUpTo("进程管理")` 实际检测是否支持中文，而不是靠字体名猜。

## 七、测试

### Q33 88 个测试都测了什么？怎么证明它们不是摆设？

7 个类：文件 22、内存 12、设备 11、指令 10、进程 13、命令 13、综合 7。

"不是摆设"体现在断言的精度：

- 进程测试断言 `PC=6、X=6、slice=6`，漏一个字段就失败；
- 文件测试断言"操作后空闲块数精确恢复"，任何块泄漏都失败；
- 综合测试断言 `all == running+ready+blocked+pending` 且 `free+used == 250`；
- 每个错误分支都有用例（重名、空间不足、只读、表满、非法指令、目录满）。

### Q34 测试怎么保证"现场恢复"真的恢复了？

`ProcessSchedulingTest.contextIsRestoredAfterSwitch`：时间片设 3，
两个 P03 交替。第 7 个时间单位时，P1 从 PC=3、X=3 继续执行，执行 `x++` 后应为
**PC=4、X=4**。如果 `restoreFrom` 漏了 X，X 会变成 1（P2 留下的值），测试立刻失败。

这是"用可观察的副作用验证内部状态"的典型写法。

### Q35 你怎么知道 FAT 那个 bug 是真 bug，而不是测试写错了？

三个证据：

1. 异常栈明确指向 `writeNewChain` 的 `chain.get(i)`，`i=205`、链长 205；
2. 用独立脚本打印出 `entries[253]=254、entries[254]=255`，而 `chainOf` 返回到 253 就停了；
3. 读完 `chainOf` 发现 `next == RESERVED` 分支，`RESERVED` 常量正是 254，
   与最后一个数据块号重合——逻辑上必然出错。

修复后同一用例通过，且新增了专门的回归测试。

## 八、局限与反思

### Q36 这个系统最大的不足是什么？如果重做会怎么改？

三个层面：

1. **文件系统**：FAT 是单字节、目录项 8 字节，导致文件名 3 字符、最大文件 64 KB。
   如果重做，会把目录项设计成 16 或 32 字节，扩展名和属性留出余量，
   并给磁盘镜像加魔数与版本号，方便格式升级。
2. **内存管理**：只有首次适配、没有分页，无法演示"虚拟内存/页面置换"。
   可以加一层"逻辑地址→物理地址"的映射，让 512 字节跑出"比物理内存更大"的程序。
3. **工程性**：界面没有自动化测试（只手工验证），磁盘镜像也没有校验和。
   如果时间允许，会引入 AssertJ Swing 做界面冒烟测试，并在 FAT 之后加一块校验区。

另外，`Fat.RESERVED = 254` 这个设计本身是"单字节空间里塞标记"的必然结果，
更干净的做法是保留块不写标记（保持 0），另用镜像头部的魔数表示"已格式化"——
这也是我在文档里标注"已知限制"的原因。
