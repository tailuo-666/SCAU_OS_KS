# 进程流程与调度细节

本文用"逐 tick 推演"的方式讲清四件事：

1. 进程的状态机（什么时候变、谁改的）；
2. 三类中断分别在什么位置处理；
3. 时间片轮转与现场保护；
4. 设备竞争、内存不足这两个最容易出错的分支。

所有推演都可以用 `OperatingSystem.runTicks(n)` 精确复现，断言写在
`ProcessSchedulingTest` / `IntegratedScenarioTest` 里。

---

## 1. 进程状态机

```
                    startProcess()
                          │
                    ┌─────▼─────┐   内存不足
                    │   READY   │◄──────────────┐
                    └──┬─────┬──┘               │
        dispatch()     │     │  时间片用完        │
                 ┌─────▼──┐  │  preemptRunning()│
                 │RUNNING │──┘                  │
                 └──┬───┬─┘                     │
      申请设备/人工阻塞│   │ end / 非法指令 / 手动撤销
                 ┌──▼───┴──┐                    │
                 │ BLOCKED │                    │
                 └──┬───┬──┘                    │
       设备完成/人工唤醒│   │                     │
                 └───┴────┴──────────────────── ┘

  另外：createProcess 时内存不足 → NEW（等内存队列）
        retryPendingProcesses 成功 → READY
        destroy → DONE（移出 PCB 池，记入完成队列，保留最近若干条）
```

| 状态 | 中文 | 在哪个队列 |
|---|---|---|
| NEW | 新建/等内存 | `pendingQueue` |
| READY | 就绪 | `readyQueue`（FIFO） |
| RUNNING | 运行 | `running` 字段（同一时刻最多 1 个） |
| BLOCKED | 阻塞 | `blockedQueue` |
| DONE | 完成 | `finishedQueue`（只保留最近 12 条） |
| （IDLE） | 闲逛 | 单独的 `idleProcess`，PID=0 |

`ProcessManager` 的五个原语一一对应：

| 原语 | 谁调用 | 做了什么 |
|---|---|---|
| `createProcess` | `startProcess` / 随机到达 | 取 PCB → 读程序 → 分内存 → 装指令 → 入就绪队列（或等内存队列） |
| `dispatch` | `OperatingSystem.dispatchNext` | 就绪队首出队，`sliceRemaining = quantum`，置 RUNNING；队列空则 IDLE |
| `preemptRunning` | 时间片中断、IDLE 让出 | 运行进程置 READY，放回**队尾** |
| `block` | 申请设备、人工阻塞 | 置 BLOCKED、记原因、入阻塞队列、清空时间片 |
| `wake` | 设备完成、人工唤醒 | 出阻塞队列 → 置 READY → 入就绪队尾（非阻塞状态调用会被忽略） |
| `destroy` | end、非法指令、手动撤销 | 出所有队列 → 回收内存 → 释放设备 → 清等待队列 → 释放 PCB |

## 2. 三类中断

| 中断 | 触发条件 | 处理位置 | 处理动作 |
|---|---|---|---|
| **程序结束中断** | 执行到 `end` | `handleProgramEnd` | 写日志 → `destroy` → `cpu.reset()` → 立刻调度下一个 |
| **时间片中断** | `sliceRemaining` 减到 0 | `handleTimeSliceInterrupt` | `saveTo(pcb)` → 置 0 → 放回队尾 → `dispatch` |
| **I/O 中断** | 某设备倒计时归零 | `handleDeviceCountdown` | 释放设备 → 唤醒原进程 → 把设备直接交给等待队列队首 |

三者的顺序体现了课程要求："进程结束时立即调度"、"时间片用完切换"、"设备完成唤醒"。

`end` 与其他指令的区别：`Cpu.executeStep` 遇到 `end` **不推进 PC**，
所以 `destroy` 后 `pcb.getPc()` 仍指向 `end` 指令本身（测试里断言为 1，而不是 2）。

## 3. 逐 tick 推演

约定：`t=n` 表示第 n 次 `tick()`；`s` 表示剩余时间片；默认时间片 6；
随机到达关闭（`new OperatingSystem(dir, seed, false)`）。

### 3.1 场景 A：最短的进程 P01（`x=10`、`end`）

| tick | ② 设备 | ③ 调度 | ④ 执行 | ⑤ 时间片 | 结果 |
|---|---|---|---|---|---|
| 1 | — | P1 投入运行（s=6） | `x=10` → X=10，PC=1 | 6→5 | P1 RUNNING |
| 2 | — | — | `end` → 撤销 P1，回收 2B | 跳过 | P1 DONE，IDLE 运行 |

断言：`ProcessState.DONE`、`X=10`、`freeBytes=512`、`finishedQueue.size()=1`。

### 3.2 场景 B：P03（8 条指令）单独运行，时间片 6

| tick | 执行 | X | PC | s | 事件 |
|---|---|---|---|---|---|
| 1 | `x=1` | 1 | 1 | 5 | |
| 2 | `x++` | 2 | 2 | 4 | |
| 3 | `x++` | 3 | 3 | 3 | |
| 4 | `x++` | 4 | 4 | 2 | |
| 5 | `x++` | 5 | 5 | 1 | |
| 6 | `x++` | 6 | 6 | 0 | **时间片中断**：保存 PC=6/X=6，放回队尾，随即又被调度（s 复位为 6） |
| 7 | `x++` | 7 | 7 | 5 | |
| 8 | `end` | 7 | 7 | — | 程序结束中断，撤销 |

关键点：`PC` 指向"下一条要执行的指令"，所以 6 条指令执行完时 `PC=6`。
这也是判断"现场是否保存正确"的最直接依据。

### 3.3 场景 C：两个 P03、时间片 3 —— 现场恢复

就绪队列初始为 `[P1, P2]`。

| tick | 运行 | 执行 | X | PC | s | 事件 |
|---|---|---|---|---|---|---|
| 1 | P1 | `x=1` | 1 | 1 | 2 | |
| 2 | P1 | `x++` | 2 | 2 | 1 | |
| 3 | P1 | `x++` | 3 | 3 | 0 | 时间片中断 → P1 READY（队尾）→ 调度 P2 |
| 4 | P2 | `x=1` | 1 | 1 | 2 | P2 从 PC=0 开始 |
| 5 | P2 | `x++` | 2 | 2 | 1 | |
| 6 | P2 | `x++` | 3 | 3 | 0 | 时间片中断 → 调度 P1 |
| 7 | P1 | PC=3 处 `x++` | **4** | 4 | 2 | 证明 X 与 PC 都从 PCB 恢复了 |

如果 `restoreFrom` 忘了恢复 X，第 7 步的 X 会变成 1（P2 的值）而不是 4。
`contextIsRestoredAfterSwitch` 就是查这个。

### 3.4 场景 D：3 个 P04（`x=20`、`!A3`、`x++`、`end`）竞争 2 台 A 设备

| tick | ② 设备倒计时 | ③④ 执行 | 状态变化 |
|---|---|---|---|
| 1 | — | P1 `x=20`（PC=1） | |
| 2 | — | P1 `!A3` → 拿到 A1（剩 3） | P1 BLOCKED |
| 3 | A1 3→2 | P2 `x=20` | |
| 4 | A1 2→1，A2 3→2 | P2 `!A3` → 拿到 A2（剩 3） | P2 BLOCKED，调度 P3 |
| 5 | A1 1→0 → **释放并唤醒 P1**；A2 2 | P3 `x=20` | P1 READY |
| 6 | A2 1 | P3 `!A3` → A1 空闲，拿到 A1（剩 3） | P3 BLOCKED，调度 P1 |
| 7 | A1 3→2；A2 1→0 → 释放并唤醒 P2 | P1 `x++` → 21 | P2 READY |
| 8 | A1 2→1 | P1 `end` → 撤销，调度 P2 | P1 DONE |
| 9 | A1 1→0 → 释放并唤醒 P3 | P2 `x++` → 21 | P3 READY |
| 10 | — | P2 `end` → 撤销，调度 P3 | P2 DONE |
| 11 | — | P3 `x++` → 21 | |
| 12 | — | P3 `end` → 撤销 | 全部 DONE，设备/内存全部归还 |

三个进程都在第 6 个时间单位**之前**提出申请，而 A1 在第 5 个时间单位就已经释放——
所以这个配置下**没有进程需要排队**。想演示"排队"，要么把设备时长调大
（如 `!A9`），要么放 4 个以上进程。测试 `threeProcessesCompeteForTwoDevices`
用的是 `!A9`，因此第 3 个时间单位就能断言"等待队列长度为 1"。

> 这是答辩时容易被追问的点：**"设备一释放就立刻交给队首"**（`handDeviceToNextWaiter`），
> 所以等待队列经常是空的。要看到队列，必须保证"申请时所有实例都还忙"。

### 3.5 场景 E：内存不足与等内存队列

用户区 512 字节，两个 300 字节的程序：

| 时刻 | 动作 | 内存分区 | 进程状态 |
|---|---|---|---|
| t0 | `run A.E`（300B） | `[0,299] P1`、`[300,511] 空闲 212` | P1 READY |
| t0 | `run B.E`（300B） | 同上（装不下 300） | P2 **NEW**，进等内存队列 |
| … | P1 执行到 `end` | `[0,511] 空闲` | P1 DONE |
| 同一 tick 的 ⑥ | `retryPendingProcesses` | `[0,299] P2` | P2 READY（PC/X 复位为 0） |

注意"同一个 tick 内"：P1 在第 ④ 步结束并释放内存，第 ⑥ 步就会重试，
所以在下一个 tick 之前 P2 已经就绪。这也是 7 步顺序的一个实际影响。

## 4. 空闲进程（IDLE）

- PID = 0，`isIdle() == true`，永远不出现在进程表里（`snapshot().all` 不含它）。
- 就绪队列为空时 `dispatch()` 返回它，CPU 就"在跑 IDLE"，时钟照常推进。
- **IDLE 正在跑但突然有进程就绪**（例如设备完成唤醒了进程），
  在同一个 tick 的第 ③ 步让出：`if (running.isIdle() && hasReadyProcess()) preempt + dispatch`。
  这样新就绪的进程不用白等一个时间单位。

## 5. 随机到达

`handleRandomArrival()` 在每 tick 的第 ⑦ 步：

1. 若 `autoArrival == false` → 直接返回（测试里都关掉，保证可复现）；
2. 倒计时 -1，未到 0 则返回；
3. PCB 已满（10 个）→ 重设 2~5 的倒计时，等下一轮；
4. 从 `\BIN` 的可执行文件里随机挑一个 → `startProcess`；
5. 重设倒计时（2~5 个时间单位）。

随机数来自构造时传入的 `seed`，所以"同样的种子 + 同样的 tick 数"结果完全相同，
界面上的"随机到达"开关只是改 `autoArrival` 布尔值。

## 6. 手动操作与自动调度的边界

| 操作 | 能否作用于 RUNNING | 能否作用于 BLOCKED | 说明 |
|---|---|---|---|
| 撤销（`killProcess`） | 可以 | 可以 | 运行中的会先 `cpu.saveTo` 再 `destroy`，然后重新调度 |
| 人工阻塞（`blockProcess`） | 可以 | 不可以 | 已阻塞的再阻塞没有意义 |
| 人工唤醒（`resumeProcess`） | 不可以 | **只能唤醒"人工阻塞"的** | 等设备的进程 `deviceType != null`，必须等设备自然完成 |

最后一条是刻意设计的：如果允许人工唤醒等设备的进程，它恢复执行后会以为自己已经"用完设备"，
而设备实际上还在别人手里，状态立刻不一致。

## 7. 常见问题排查

| 现象 | 原因 | 看哪里 |
|---|---|---|
| 进程一直 READY 不动 | 就绪队列里排在别人后面，或时间片设为很大 | `snapshot().ready` |
| 进程一直 BLOCKED | 设备被占满且时长为 9，需要等 | 设备区的"剩余"列 |
| 进程停在 NEW | 内存不够（程序字节数 > 最大空闲分区） | 内存区最大空闲块 |
| 完成队列里 X 不符合预期 | 少算/多算 `end` 前的指令，或 X 在上界 255 饱和 | 日志里每条指令的 X |
| 时间片切换次数比预期少 | 程序指令数 ≤ 时间片 | `type` 看指令条数 |
